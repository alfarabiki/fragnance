# ATLASE — Observability

## 1. Logging Framework

| Property | Value |
|----------|-------|
| Format | Structured JSON (one object per line) |
| Transport | `stdout` → Cloudflare Workers Logs / Supabase Logs / Log drain |
| Library | `pino` (Node.js) — lightweight, high-throughput |
| Log levels | `debug`, `info`, `warn`, `error`, `fatal` |
| Request tracing | Every request gets a `traceId` (UUID v4) injected at middleware |
| Trace propagation | `traceId` is set in response header `X-Trace-Id` for debugging |

### Middleware Trace Injection

```ts
// middleware.ts
import { NextResponse } from 'next/server'
import { randomUUID } from 'crypto'

export function middleware(request) {
  const traceId = request.headers.get('x-trace-id') || randomUUID()
  const response = NextResponse.next()
  response.headers.set('X-Trace-Id', traceId)
  // Attach traceId to request context for downstream handlers
  request.headers.set('x-trace-id', traceId)
  return response
}
```

### Log Structure

```json
{
  "level": "info",
  "time": "2026-09-01T10:30:00.000Z",
  "traceId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "service": "atlase-web",
  "message": "order_created",
  "context": {
    "orderId": "...",
    "totalIdr": 149000,
    "paymentMethod": "bank_transfer",
    "channel": "web"
  }
}
```

## 2. Application Logs

| Log Event | Level | Trigger |
|-----------|-------|---------|
| Server startup | `info` | Next.js serverless function cold start |
| Request served | `info` | Every API route / page render (sampled in production) |
| Cache hit/miss | `debug` | ISR / CDN cache status |
| Product page rendered | `info` | `/aroma/:slug` SSR/ISR render |
| Customization saved | `info` | User completes customization flow |
| Cart updated | `info` | Item added / removed from cart |
| Validation error | `warn` | Input validation failure (not server error) |
| Database query slow | `warn` | Query exceeds 500ms threshold |
| Unhandled exception | `error` | Uncaught error in request handler |
| External service failure | `error` | Midtrans / Supabase / Redis timeout or error |

**Sampling:** In production, `info`-level request logs are sampled at 10% to control volume. All `warn` and above are always logged.

## 3. Error Tracking

| Property | Value |
|----------|-------|
| Tool | Sentry (self-hosted or cloud) |
| Environment | Separate DSN per `staging` / `production` |
| Source maps | Uploaded to Sentry on each deploy (via CI); not publicly accessible |
| Release tagging | Git commit SHA as Sentry release version |
| Alert rules | See §8 |

### Sentry Integration

```ts
// sentry.client.config.ts
Sentry.init({
  dsn: process.env.SENTRY_DSN,
  environment: process.env.NODE_ENV,
  release: process.env.COMMIT_SHA,
  tracesSampleRate: 0.2,       // 20% of transactions for performance
  replaysSessionSampleRate: 0, // No session replay in production
  replaysOnErrorSampleRate: 1.0,
  beforeSend(event) {
    // Strip any PII that accidentally ends up in error context
    if (event.request?.cookies) {
      delete event.request.cookies
    }
    return event
  },
})
```

### Source Maps

- Generated by Next.js build (`next build` produces `.map` files).
- Uploaded to Sentry via `@sentry/nextjs` build step in CI.
- **Never** served publicly (`X-Content-Type-Options: nosniff` + no public route to `.map` files).

## 4. Payment & Webhook Logging

### Payment Logs

| Field | Logged | Redacted |
|-------|--------|----------|
| `orderId` | ✅ | — |
| `paymentMethod` | ✅ | — |
| `amountIdr` | ✅ | — |
| `status` | ✅ | — |
| `midtransTransactionId` | ✅ | — |
| `fraudStatus` | ✅ | — |
| `cardNumber` | ❌ | **NEVER** |
| `cardToken` | ❌ | **NEVER** |
| `bankAccount` | ❌ | **NEVER** |
| `rawWebhookPayload` | ✅ (full) | Card/bank fields stripped before storage |

### Webhook Logs

```json
{
  "level": "info",
  "message": "midtrans_webhook_received",
  "context": {
    "traceId": "...",
    "orderId": "...",
    "transactionId": "...",
    "statusCode": 200,
    "processingTimeMs": 45
  }
}
```

- Webhook logs include the full request body **after** redacting payment secrets.
- Webhook processing time is tracked for SLA monitoring (target: < 500ms).
- Failed webhooks are retried (Midtrans retry policy) and logged at `error` level with retry count.

## 5. Audit Logs

Audit logs are a **separate concern** from application logs — stored in a dedicated `audit_logs` table in Supabase, not in the logging pipeline.

| Field | Type | Description |
|-------|------|-------------|
| `id` | UUID | Primary key |
| `actor_id` | UUID | User who performed the action (or `system`) |
| `action` | text | e.g., `order.status_changed`, `product.price_updated`, `admin.user_promoted` |
| `target_type` | text | `order`, `product`, `user`, `settings` |
| `target_id` | UUID | ID of the affected entity |
| `before` | jsonb | State before change |
| `after` | jsonb | State after change |
| `created_at` | timestamptz | When the action occurred |
| `ip_address` | inet | Actor IP (redacted in exports) |

**Rules:**

- Audit logs are append-only — no update or delete operations.
- Queried only for compliance, dispute resolution, or security investigations.
- Retained for **24 months** (Indonesian PDP record-keeping guidance).

## 6. Metrics

| Metric | Type | Source | Alert Threshold |
|--------|------|--------|-----------------|
| API latency (p50, p95, p99) | Histogram | Sentry Performance / custom | p99 > 2s |
| Error rate (5xx) | Counter / rate | Sentry + Cloudflare | > 1% of requests |
| Payment success rate | Gauge | Supabase `orders` | < 95% |
| Payment failure rate | Gauge | Supabase `orders` | > 5% |
| Webhook processing time | Histogram | Application logs | p99 > 2s |
| Queue backlog | Gauge | Supabase / Redis | > 100 pending |
| Active connections | Gauge | Supabase | > 80% pool capacity |
| ISR revalidation lag | Gauge | Next.js build manifest | > 1 hour stale |

### Metric Collection

- **APM:** Sentry Performance traces (transactions for each page load / API call).
- **Infrastructure:** Supabase Dashboard built-in metrics.
- **Custom:** SQL queries against `analytics_events` and `orders` tables for business metrics (refreshed daily via cron or manual query).

## 7. DB Monitoring

| Concern | Tool / Method | Frequency |
|---------|---------------|-----------|
| Connection pool usage | Supabase Dashboard → Database → Connection pool | Real-time |
| Slow queries | Supabase `pg_stat_statements` view | Daily review |
| Query performance | Supabase Dashboard → Database → Query performance | Real-time |
| Table bloat | `pg_stat_user_tables` — dead tuple count | Weekly |
| Index usage | `pg_stat_user_indexes` — unused indexes | Monthly review |
| Storage growth | Supabase Dashboard → Database → Disk usage | Weekly |
| Replication lag | Supabase Dashboard (if using read replicas) | Real-time |

**Slow query threshold:** Queries exceeding **500ms** are logged at `warn` level with the full SQL (redacting any parameter values that might be PII).

**Index discipline:** Every foreign key and frequently filtered column (`products.slug`, `orders.user_id`, `analytics_events.timestamp`) must have an index. New queries are reviewed for missing indexes before merge.

## 8. Alerting & On-Call Basics

| Alert | Condition | Channel | Urgency |
|-------|-----------|---------|---------|
| High error rate | 5xx > 1% for 5 min | Slack + PagerDuty | P1 — immediate |
| Payment failure spike | Failure rate > 10% for 15 min | Slack + PagerDuty | P1 — immediate |
| API latency spike | p99 > 3s for 5 min | Slack | P2 — within 1 hour |
| Webhook processing slow | p99 > 2s for 10 min | Slack | P2 — within 1 hour |
| DB connection pool saturation | > 90% for 5 min | Slack + PagerDuty | P1 — immediate |
| Sentry new error spike | > 20 new issues/hour | Slack | P2 — within 1 hour |
| ISR staleness | Catalog pages > 2 hours stale | Slack | P3 — next business day |
| Disk usage | > 80% | Slack | P3 — next business day |

**On-call rotation:**

- Single on-call engineer initially (small team).
- Escalation: acknowledge within 15 min → investigate within 30 min → resolve or mitigate within 2 hours.
- Post-incident review for any P1 alert.

## 9. Data Retention

| Log Type | Retention | Reason |
|----------|-----------|--------|
| Payment logs | **> 12 months** | Financial compliance, dispute resolution |
| Webhook logs | **12 months** | Payment reconciliation, retry debugging |
| Audit logs | **24 months** | PDP compliance, security investigations |
| Application logs | **> 30 days** | Operational debugging |
| Error tracking (Sentry) | 90 days (Sentry default) | Bug fixing, regression detection |
| Analytics events | 14 months (GA4 setting) | Business reporting |
| Performance metrics | 90 days | Trend analysis |

**Archive strategy:** After retention period, logs are exported to cold storage (Supabase Storage or Cloudflare R2) and deleted from the primary store.

## 10. What Must NEVER Be Logged

| Data Category | Examples | Reason |
|---------------|----------|--------|
| Payment credentials | Card number, CVV, card token, bank account number | PCI-DSS / financial security |
| Authentication secrets | Passwords, password hashes, session tokens, JWT secrets | Account security |
| API keys & tokens | Midtrans server key, Supabase service key, Sentry DSN (client-side) | Infrastructure security |
| Customer PII | Full name, email, phone number, home address | Indonesian PDP compliance |
| Raw webhook bodies (unredacted) | Full Midtrans payload with card data | PCI-DSS |
| Encryption keys | Any key used for signing or encrypting data | Infrastructure security |
| Internal IDs in public context | Supabase UUIDs in user-facing error messages | Information leakage |

**Redaction pattern:** If PII or secrets accidentally appear in a log, the redaction middleware replaces values with `[REDACTED]`. Sentry's `beforeSend` hook strips cookies and headers.

**Enforcement:** A linter rule (`eslint-plugin-no-secrets`) scans for patterns like API keys, card number regexes, and email patterns in log statements before merge.
